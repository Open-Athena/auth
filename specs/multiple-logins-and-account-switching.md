# Multiple logins, account switching, and incoming link credentials

Status: implementation started. The standalone selection-context codec and mutation guard are built in `src/core/selection-context.ts`; registry, retained-login storage, integration and UI remain unbuilt. Origin: the CW storage dashboard's detailed OpenGraph sharing discussion on October 13, 2026. This is upstream library work for `@open-athena/auth`, not a CW-specific account picker or an instruction to change a live deployment. The user authorized starting implementation; this documentation subtask makes no code changes or commits. Update the spec alongside implementation phases, then move it under `specs/done/` with the completed implementation. Deployments and live migrations require separate authorization.

## Goal and first-class simplicity requirement

Let a browser retain multiple independently authenticated identities and switch the active account without repeatedly signing out and signing back in. Incoming share-link credentials are another candidate in the same selection model, rather than a special case that overwrites the existing login. Supply reusable backend/session machinery, headless React hooks, and an optional account picker; consumers control presentation and selection policy.

Multi-account support must degrade gracefully to a single login with zero added interaction complexity. An ordinary one-account user sees the same sign-in, identity chip, profile editing, page, and sign-out behavior as today: no obligatory picker, account-count badge, intermediate confirmation, or account-management screen. Applications that do not enable the feature must not acquire a mandatory session registry, migration, or new UI. An application that enables it must not need to write separate single-account and multi-account flows.

## Motivation and current source evidence

- `src/core/session.ts` signs one subject per cookie (`e:<email>` or `g:<grant_id>`); another sign-in or redemption replaces that cookie. A grant's subject attribution is not proof that its bearer owns the attributed person's account.
- `src/core/gate.ts` authenticates an explicit Bearer/query token ahead of the cookie. `redeem()` spends a redemption and returns a grant-session cookie without preserving the previous session.
- `src/react/exchange.ts` strips `key=` synchronously and exchanges it before `AuthGate` probes identity. Consequently a logged-in member following a guest link can be demoted to that guest identity.
- `src/react/WhoamiChip.tsx` supports a profile-opening callback, but no retained-account roster or switching. `src/react/useWhoami.ts` caches the current identity, not independently selected accounts.
- [The existing session-registry proposal] already describes optional `SessionStore` support. Reconcile with that work; do not invent a second competing device-session registry.

The motivating CW use cases are a signed-in member following a guest link without losing their member identity, retaining two legitimate personal/work logins, and choosing an explicitly different guest identity when needed. Preview-only `og=` credentials are not logins: they authorize detailed unfurls of an exact view and must never become accounts or change dashboard authentication. `og=` handling and arbitrary preview-token TTLs belong to the consuming application's OG subsystem, not this auth feature.

## Model: available identities are not combined authority

Distinguish a principal (verified email account or grant), a session (authentication evidence for that principal), a browser's retained login set, its active selection, and a pending incoming credential. An account picker may group multiple valid sessions for the same verified principal; different grant IDs remain different identities even if their display name/email matches. Do not merge an attributed guest with a verified email account based on matching profile fields.

Retaining several logins does not authorize a request as all of them. Each request has one selected actor and is authorized against that actor's currently valid scopes. There is no implicit scope union, global strongest-role ordering, or cross-account privilege escalation. Consumer policy may compare capabilities for the requested resource, but must ultimately select one candidate or require a choice. Preserve the identity the user explicitly selected, including a deliberate lower-privilege guest selection, rather than automatically switching back to an administrator on the next request.

Logging in to another account, switching, and adding a link-derived identity must preserve other valid retained logins. A switch selects existing authentication evidence; it never refreshes expired evidence or allows a client-supplied email/role/subject to manufacture an identity.

## Configurable resolution, not a three-value enum

Provide an extensible server-side resolution policy over validated candidates, active selection, incoming-credential origin, requested resource/capability where the consumer supplies it, and whether the selection is an explicit user choice or an automatic decision. A decision can retain/select an available identity, request user disambiguation, require sign-in/re-authentication, or reject the incoming credential. Helper policies are useful, but the public API must not constrain consumers to `prefer-session | prefer-link | ask`.

The recommended browser-link default preserves a valid active account, with no chooser merely because `key=` is present. A valid guest link remains available as an alternative; it does not automatically replace the account, merge its permissions, or spend a new redemption just to display the alternative. With no usable retained login, a valid guest link can establish the first login directly. If the active identity cannot access the target, the consumer may prompt with relevant alternatives or explicitly configure a fallback; the library must not silently escalate or demote based on an invented role hierarchy.

An implementer may always retain the prior user, always offer a chooser when identities differ, automatically choose a candidate authorized for a particular resource, or define another safe policy. The same candidate model powers ordinary account switching and incoming-link disambiguation. Selection is server-enforced; an application-provided modal only gathers a choice, not authority. Consumers may disable retaining unused incoming guest credentials, or ask before retaining them, independently of which account stays active.

Explicit `Authorization: Bearer` on a script/API request remains a deliberate request-scoped credential and must not be overridden by an incidental browser cookie. Browser `key=` navigation resolution is a separate policy seam; audit all server query-token handling as well as the React exchange path so the two do not disagree. Invalid explicit API credentials must not silently fall back to a cookie. Crawlers inspecting a valid bearer link for an unfurl must not establish a browser session or spend a redemption.

## Session persistence and backend contracts

Implement a bounded, authenticated, origin/gate-scoped retained-login set with an active-selection version. Never put session secrets or raw share tokens in localStorage, readable account-list payloads, analytics, or audit rows. An intentionally shared `key=` URL necessarily carries its credential; claim/strip it early and do not propagate it into unrelated URLs or account selectors. JavaScript receives safe display metadata and opaque selectors, not reusable retained-login credentials. An account-list endpoint must expose only sessions proven to belong to that browser's login set, not enumerate arbitrary accounts or sessions by guessed identifiers.

Phase 1 proposes an opt-in HttpOnly opaque browser handle backed by the optional session-store substrate, not a client-held roster or per-account cookies. The storage and integration contracts below remain unbuilt; the standalone selection-context codec and mutation guard are implemented. Keep the existing single-session/stateless path usable without it. Persistent cookies must retain current Secure/HttpOnly/SameSite and gate-isolation guarantees.

An incoming link can be validated for a candidate description without redeeming it. If user choice is pending after the URL is stripped, retain proof using a short-lived browser-bound server context or equivalent protected mechanism; a grant ID alone is not proof of possession. Pending metadata confers no access. On selection, revalidate grant status and atomically redeem only when establishing a new session. A repeated click, React StrictMode invocation, or selecting an existing guest session must not double-spend redemptions or bypass caps. Grant preview metadata must not identify accounts to an invalid-token holder.

Validate the selected session on every authenticated request using the existing live email policy/grant checks; revalidate inactive candidates before selecting them. Expiry, grant disable versus revoke semantics, rotation epochs, and optional registry revocation retain their existing meanings. Switching must not extend a session's expiry. Invalidating one login must not destroy unrelated retained logins. An invalid active selection must not silently activate a different, more powerful identity.

Provide backend/headless contracts for listing safe candidates, selecting a retained session, adding a proven login, resolving an incoming credential, signing out the active login, and signing out this browser's whole retained set. Wire OIDC and email-code callbacks to add/select using the same model. Normal sign-in selects the newly authenticated account without erasing the old one. A provider's account chooser and this app's retained-account picker are distinct: adding an account still needs genuine IdP/email proof, with the existing callback/state/nonce protections.

Sign out means ending/removing the selected browser login, not revoking the underlying guest grant for everyone. Sign out all affects this browser's retained set, not every device's sessions unless a separately authorized device-revocation action requests that. Removing the active account must not quietly reactivate an inactive administrator: leave signed out or apply an explicitly documented consumer selection policy.

## Tabs, requests, and caches

### Phase-1 persistence and concurrency contracts

- **Opt-in and migration.** `sessions?: SessionStore` enables registry-backed sessions; a separate `retainedLogins` option enables browser retention and requires the store's atomic retained-login capability. Neither option is enabled implicitly. With neither configured, existing cookies, routes and zero-config single-login behavior remain unchanged, with no new header, table, read or migration requirement. Registry-only consumers need no account picker. Enabling retention requires an explicit migration and compatible adapter; missing capabilities fail configuration rather than falling back to unsafe independent writes. A valid legacy cookie may be imported once through a protected bootstrap, preserving its original `iat`/`exp` and live policy checks; it must not redeem a grant again or extend evidence lifetime. After bootstrap the retained-mode gate ignores the legacy cookie, and logout clears it, so it cannot resurrect a removed login.
- **Data and cookie boundary.** Keep one browser-set row with gate identifier, handle hash, nullable active session ID, monotonic `selectionVersion`, creation time and absolute expiry. Retained session rows carry browser-set membership, principal, original issued-at, absolute session expiry and revocation state. Pending-link rows are a distinct record type from email-code `pending_auth`, carrying browser/gate binding, token hash, expiry, consumption result and operation ID. Generate handles with at least 256 random bits; store only a keyed hash of the handle, never expose it in JSON, and keep the raw handle only in the HttpOnly cookie. Selectors are random non-credential IDs, meaningful only with matching browser membership. The cookie contains no active actor or roster, stays constant across switches, and uses the configured gate-specific name/path; shared-origin mutually untrusted apps require separate origins, not merely different cookie names. Stale responses cannot restore an old selection through `Set-Cookie`.
- **Snapshot and CAS.** Identity/account snapshots expose a selection context `{ browserSetId, sessionId, version }` alongside gate identity, safe candidates and pending metadata, with `Cache-Control: no-store`; `sessionId` is nullable when signed out. Versions are nonnegative safe-integer numbers, excluding negative zero, monotonically incremented through `nextSelectionVersion()` and never reset/reused within a browser set. At `Number.MAX_SAFE_INTEGER`, fail closed or establish a new unique browser-set ID; never wrap. Browser-set IDs must not be reused across gates. Every add/select/remove/logout/resolve operation supplies the expected context and a browser-bound operation ID. Membership, capacity, target validity and version are checked at the authoritative write boundary; success commits all affected rows together. Any roster change, active-identity change or pending-candidate change advances the version, even A → B → A; last-seen updates do not. Concurrent unrelated additions never overwrite each other: one may receive a conflict and explicitly retry against a fresh snapshot. An exact operation replay returns its recorded result without reapplying selection or returning an obsolete snapshot as current. Reusing an operation ID with different input fails.
- **Stale mutations.** In retained mode the planned integration helper attaches `X-OA-Selection-Context` to cookie-authenticated application mutations and auth-state mutations; selection endpoints additionally name the intended selector. The implemented `serializeSelectionContext()` produces canonical unpadded base64url JSON with exactly `{ browserSetId, sessionId, version }` in that key order. This is not encrypted or signed: the context contains only safe selectors and a concurrency assertion, never authority. IDs are nonempty strings of at most 256 characters; the encoded header is at most 2048 characters. The parser rejects noncanonical encodings, extra JSON fields, malformed values and invalid versions. After authentication/authorization and before side effects, `checkSelectionContext()` compares the supplied context against the caller's validated current browser/gate selection. Missing, malformed or stale context uniformly returns `409` with `{ error: 'selection_context_conflict', recoverable: true, action: 'refresh_selection' }`, JSON content type and `Cache-Control: no-store`, with neither business nor auth-state side effects. The planned client integration refreshes identity, invalidates private caches and asks for user resubmission; it never retries a mutation automatically as another actor. Missing/invalid authentication remains `401`, and an authenticated but unauthorized actor remains `403`. Explicit Bearer requests stay request-scoped and do not require this browser header. Same-origin/CSRF checks remain separate requirements. The standalone guard neither authenticates nor implements a store/CAS lock, and a matching `sessionId: null` confers no authority.
- **Request boundary, not distributed transactions.** Authenticate and validate the supplied version from an authoritative snapshot before invoking a consumer mutation handler, then pin that request's actor. A switch committed before that check causes a conflict; a switch after that check does not relabel the in-flight request. This does not cancel already admitted work or atomically commit a consumer's business database with auth storage. Consumers needing stronger exclusion must coordinate at their own write boundary. Do not cache the selection check or serve it from a potentially stale replica. Registry revocation and live policy checks are also required; the version is not an authorization epoch for all external policy changes.
- **Tabs and data.** Use `BroadcastChannel` invalidation notices scoped by origin/gate, with focus/visibility revalidation as recovery when notices are missed or unsupported. Notices carry no credentials or trusted identity; recipients fetch server truth. Partition application queries by gate and selected session, discard late responses from prior identity generations, and expose a headless transition event before rendering the new account's private data. No per-tab selection adapter is required in phase 1.

### Phase-1 incoming-link commit contract

Validation hashes the presented token and creates a short-lived browser-bound pending context without incrementing `redeems`, minting a session or changing the active actor. Store the token hash captured at validation, not just the grant ID: rotation between validation and selection must invalidate the old proof even when existing sessions survive rotation. Pending metadata is not authority, and expired contexts require presenting the link again. Checking a valid but exhausted link may describe it as unavailable, never as a guaranteed future login.

Expose one adapter-level `commitIncoming` operation (name provisional), not a core sequence of `consumePending(); redeem(); insertSession(); select()`. Within one atomic storage boundary it must recheck pending browser/gate binding, expiry and proof hash, current grant lifecycle and redemption cap, expected selection version and capacity; then consume the pending proof, increment the grant exactly once if a new session is needed, insert the session/membership, record the idempotent result, and apply the chosen selection/version. Failure leaves all these unchanged. Reusing a still-valid retained session for that grant consumes no redemption, even if the link is now disabled, expired or exhausted; it is an existing-session selection, not permission to mint replacement evidence. Revocation, session expiry and rotation epochs still invalidate that session. Keeping the current member active while adding a guest must be an explicit resolution outcome, not an unconditional side effect of opening a link.

Concurrent duplicate submissions return the same resulting session and at most one redemption; another operation competing for a one-use grant has exactly one winner. A lost HTTP response does not roll back a committed redemption: retrying the same browser-bound operation discovers its result without reselecting an account after a later switch. Retain results for the retry window below; after it expires a replay fails closed, not as a fresh redemption. Anonymous bootstrap must establish the browser handle before submitting the commit, so a lost response does not lose the only recovery credential. Simultaneous bootstrap responses may orphan an empty set; they must never create/redeem sessions before the browser has a stable handle.

**D1 feasibility gate.** Today's `d1GrantStore.redeem()` is a single guarded `UPDATE ... RETURNING` protecting only the counter. `gate.redeem()` signs a cookie afterward; `PendingAuthStore.consume()` separately claims email-code proof before `gate.signIn()`. None implements the combined contract above. [D1 batch documentation] provides transactional prepared-statement batches, not an interactive JavaScript transaction around arbitrary `await`s; `withSession()` is not a SQL transaction. In particular, a guarded update affecting zero rows is not a SQL error and does not automatically roll back the rest of a batch. A proposed D1 adapter must demonstrate SQL-level dependencies/constraints that make every dependent write conditional on the same winning operation, with full rollback on failure, on the same D1 database. Batch result inspection after commit cannot repair partial success. Separate store instances/databases or external policy callbacks cannot be made atomic by this interface. Reject unsupported configurations; checkpoint a proven SQL design and concurrency/failure tests before implementation is accepted, rather than promising transactions the existing adapter does not expose. Email-code proof consumption plus registry session creation needs its own equivalent atomic completion capability; do not claim the current consume/sign-in sequence already provides it. Provider/network validation stays outside the SQL boundary, with proof binding and replay protection carried into the commit.

### Phase-1 lifetime, capacity and collection contracts

- **Lifecycle matrix.** At `now >= expiresAt`, a link cannot establish a new session. Existing retained sessions remain selectable through their own expiry when `expiryEndsSessions: false`; with `true`, live link expiry invalidates them. Disabling blocks new redemption but not existing-session use/selection. Revocation always invalidates existing sessions; rotation without `endSessions` invalidates pending old-token proof but preserves existing sessions, while `endSessions` additionally enforces the existing `iat < sessionsInvalidBefore` cutoff. Exhaustion never kills existing sessions. All sessions enforce their own absolute expiry, registry revocation and live email policy/grant checks on every request. Switching and touching last-seen never renew them. `sessionTtlS` updates apply to future sessions only; shortening existing sessions requires an explicit registry operation. A newly invalid active login becomes signed out, not an automatic selection of another retained account.
- **Proposed defaults, configurable downward or upward with explicit bounds.** Limit each browser/gate to 8 retained sessions and 4 live pending contexts. Pending TTL is 10 minutes, capped by the link's expiry when present; completed operation results live for 24 hours. Browser handles expire absolutely after 30 days, never sliding on switch, with cookie Max-Age no greater than the remaining browser lifetime. A session's effective browser usability ends at the earlier of its own expiry and browser-set expiry. Bounds apply atomically, not through count-then-insert. At capacity return `409` with `{ error: 'retained-login-capacity' }` or `{ error: 'pending-link-capacity' }` and preserve every valid login, selection, pending proof and redemption count; the user explicitly removes an entry before retrying. Reusing an existing valid session needs no extra slot. Remove only expired/revoked entries opportunistically; no silent eviction of valid inactive or active accounts.
- **Cleanup and abuse limits.** Logical expiry/revocation is enforced immediately whether or not physical cleanup ran. Provide an explicit, idempotent bounded cleanup operation, defaulting to at most 200 rows per call with indexed expiry/collection keys and a continuation cursor. Collect expired pending proof, expired retry records, revoked/expired session rows and expired/orphan browser sets without dropping a live retry record's result prematurely; audit retention is independent. Consumers schedule hourly cleanup or equivalent bounded maintenance, and document the scheduler requirement (no implicit cron in Pages Functions). Gate-wide pending/bootstrap rate and storage quotas are required in addition to per-browser caps, since attackers can create many browser handles; enabled retention configuration must supply finite deployment-specific limits and fail closed with `429` for rate or `503` for storage pressure, before consuming proof or redemptions. Authorization must not depend on cleanup or best-effort last-seen writes.

Ship a clear default: active selection is browser/gate-wide, and tabs learn of switching/sign-out through a supported notification mechanism plus server revalidation. They refresh identity and stop presenting stale-account data. A per-tab selection adapter can be supported without changing the core candidate model, but must not be accidental behavior or mandatory for the first release.

Handle the account-switch race explicitly. A form opened as A must not submit as B merely because another tab changed the shared server-side selection. Mutating requests must bind their intended session/selection version and reject a stale context before performing side effects; consumers need a documented integration helper and a recoverable conflict response. In-flight requests retain the actor selected when that request was authenticated. Never replay a stale mutation automatically under another identity.

Whoami/account-list caches and application data caches must be scoped/invalidateable by gate and selected session, including authorization changes. Profile edits, avatars, staging selections, optimistic mutations, and unsaved forms must not bleed between accounts. Hooks must expose an identity transition suitable for consumers to clear or partition private caches, with explicit pending/error states; do not require every consumer to reconstruct the lifecycle from cookie timing. Concurrent add/switch/remove operations must preserve unrelated entries and reject stale selections instead of last-write-wins loss of accounts.

## React/user-chip behavior

Offer headless account/session hooks and an optional unstyled, accessible account picker consistent with the current package's labels/classNames/render customization. The consumer may use the same picker as a modal, popover, or its own page. Link disambiguation should reuse it with incoming-link context and a safe action label, not introduce a separate identity chooser.

When multiple identities are available, clicking the user chip can offer Profile, Switch account, Add account, Sign out this account, and Sign out all. Switch account leads to a list with the current account selected, names/avatars, verified-account versus guest-link provenance, and useful expiration/permission summaries; names and avatars alone must not disguise a guest as a verified person. Keep profile editing accessible rather than unconditionally changing the existing chip callback into an account picker.

With one login and no pending alternative, preserve the existing chip/profile action and normal sign-out UX. Consumers enabling add-account discovery may expose an unobtrusive Add account action, but there is no mandatory intermediate picker or empty list. When a second login is actually added, the same components expose switching without extra consumer branches. With zero logins, render the existing sign-in panel; one valid guest link can enter directly unless consumer policy explicitly requires confirmation. Canceling disambiguation preserves the current identity and page state.

## Security and audit

New add/select/remove/exchange endpoints mutate authentication state: apply same-origin/CSRF protections, validate browser-set membership and pending proof server-side, and never allow a GET or a displayed candidate's metadata to switch accounts. IdP callback completions remain intentional authenticated flows, not exceptions allowing arbitrary candidate selection. Rate-limit candidate validation and pending contexts; bound both entries and contexts to avoid resource exhaustion.

Audit the actual selected actor for reads/mutations, and record intentional add/switch/remove decisions with safe identifiers and enough old/new selection context for attribution. Candidate validation is not a redemption, sign-in, impersonation, or authenticated view by that candidate. Do not log the raw incoming token. Where an action involves an incoming grant while the current member stays active, distinguish actor from referenced grant rather than claiming the member acted as its attributed guest. Define retention and collection under the package's existing audit/privacy controls.

## Acceptance tests and demo

Use exact structured assertions for identities, cookies/store changes, redemption counts, audit events, and HTTP results. Browser-test the interaction flows, not just pure policy helpers.

1. Existing single-login consumer works unchanged with no registry or mandatory migration. Zero/one-login FE has no additional picker step; current profile and sign-out behavior remain usable.
2. Sign in as A, add B, switch A → B → A without new provider authentication or lost sessions; grant-backed and verified-email identities remain distinguishable.
3. Valid active member plus guest link preserves the member by default, without redeeming the unused link; selecting the guest explicitly preserves the member for later switching. A consumer-defined chooser and custom selection policy exercise the same server-backed candidates.
4. Anonymous plus valid guest link establishes one session once. Invalid/expired/revoked/disabled/exhausted links cannot establish access; a bad browser link does not log out a valid member. Validate and selecting an existing session do not spend redemption caps; duplicate/concurrent exchanges are idempotent.
5. An `og=` preview credential never appears in the account list, mints a session, or changes the active actor. Explicit API Bearer semantics remain request-scoped and fail closed.
6. Revocation, session expiry, link expiry with `expiryEndsSessions: true`, and rotation's issued-at cutoff reject affected retained sessions; unrelated accounts still work. Disable, exhausted caps, expiry with `expiryEndsSessions: false`, and rotation without `endSessions` preserve otherwise-valid existing sessions. Recheck live email policy on selection/requests. Matching display names/emails do not merge distinct principals, and no request obtains a union of scopes.
7. Sign out this account versus all browser logins has distinct exact results; neither revokes a shared grant globally. Removing an active guest does not silently activate a retained administrator.
8. Switching in tab B updates tab A's chip/data; a stale A form cannot mutate as B. Cache/optimistic data and profile fields do not cross identities. Concurrent additions preserve both sessions; stale selector/version requests fail without side effects.
9. Browser-set IDs, session selectors and pending contexts from another browser/gate cannot list/select accounts or redeem links. CSRF, forged/replayed contexts, callback mix-ups, limits/cookie size and expiry boundaries fail closed.
10. Existing auth demo adds a real multi-account walkthrough, guest-link conflict, and a selectable consumer-policy example, alongside the unchanged single-account demo. Verify keyboard navigation, focus restoration, cancellation, zero/one/multiple accounts and mobile layout.
